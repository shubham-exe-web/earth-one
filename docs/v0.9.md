# Earth One v0.9 — Event Intelligence Layer

## Objective

v0.9 changes the unit of analysis from individual pixels to **disturbance
events**.

```text
pixel evidence
      ↓
connected components
      ↓
event boundary
      ↓
event attributes
      ↓
reference matching
      ↓
event catalog
```

## Event definition

A candidate event is a connected component of pixels satisfying:

`finite(change) AND score >= threshold`

The component can use 4- or 8-neighbour connectivity.

Small components can be discarded using a minimum-pixel threshold.

This threshold is a configurable engineering parameter and should be calibrated
to the sensor resolution and minimum mapping unit of the scientific study.

## Event attributes

Each event receives:

- event ID
- pixel count
- area in m²
- area in hectares
- mean index change
- mean disturbance evidence score
- pixel bounding box
- optional polygon geometry

The event raster gives each mapped event a persistent integer ID.

A GeoJSON representation is also generated when requested.

## Reference matching

v0.9 can match event polygons/IDs to a spatial reference-label raster.

For each event it calculates:

- reference class
- reference-covered pixels
- majority-reference agreement

This is an event-level validation bridge.

It does not assume that the reference data are perfect.

## Why event objects matter

Pixel-level classification is difficult to interpret operationally.

An event has:

- location
- size
- boundary
- magnitude
- time context
- class
- confidence
- reference evidence

That makes it possible to track the same disturbance through subsequent
observations.

## Carbon-accounting bridge

The event object is the correct place to attach future variables such as:

- land-cover class
- biomass before event
- biomass after event
- biomass difference
- carbon fraction
- carbon loss
- uncertainty
- recovery trajectory

Therefore v0.9 creates the data structure needed for the eventual carbon layer
without pretending that carbon can be estimated from disturbance evidence alone.

## Next: v1.0

The next major version should become the first complete autonomous event pipeline:

```text
acquire
  ↓
preprocess
  ↓
detect
  ↓
classify
  ↓
validate
  ↓
segment event
  ↓
track event over time
  ↓
estimate biomass/carbon
  ↓
propagate uncertainty
  ↓
generate research-ready observation
```

v1.0 should also introduce persistent event IDs across dates, rather than treating
each observation independently.
